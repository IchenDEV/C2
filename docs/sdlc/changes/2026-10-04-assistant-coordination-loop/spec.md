# Spec: Bidirectional, versioned assistant coordination

## Design

用户已明确要求继续实施本方案。下列能力通过同一 Core 服务提供；公开名称随现有 command/MCP 契约收敛，实际实现和证据记录在 Verification。

## 1. 实施前审计与成本判断

下表记录实施前的历史基线。缺口已按后续章节实施；当前运行证据见 [Verification](verification.md)。

| 当前实现 | 核实的能力与缺口 | 处理 |
| --- | --- | --- |
| [assistant runtime](../../../../crates/core/src/plugins/app/plugins/assistant.rs) | dispatch/link/update/accept；运行中只看状态，已分配会话仅 idle/failed 时提取最后一轮文本；一个全局 attention 可让整个幕僚停止 | 用双向消息、问题和任务级决策替换单次派工协议；局部阻塞不冻结其他项目 |
| [assistant state](../../../../crates/core/src/assistant.rs) | 修改标题/验收只更新记录和修订；不会向正在工作的会话发送变更；无 assignment 的需求版本 | 增加目标语义版本、变更记录及执行者确认，禁止旧版本结果通过新要求验收 |
| [Engine commands](../../../../crates/core/src/plugins/app/plugins/engine.rs) | engine.steer / engine.queue / engine.answer_elicitation / engine.answer_permission 存在；queue 是内存 HashMap，出队提交错误被丢弃 | 持久投递由 Engine 命令层唯一负责；普通输入与幕僚复用同一队列，不增加私有提示队列 |
| [native steering](../../../../crates/core/src/engine.rs) | Provider 宣告 steering 才可用；injected/startedNewTurn 是传输结果，持久文本写入在调用后 | 不声称所有 Provider 支持即时交流；补幂等投递与未知结果核对 |
| [question/activity](../../../../crates/core/src/activity.rs) | 已有结构化问题、权限等待及 oneshot 回答通道 | 保留会话级问题来源；增加幕僚路由和持久问题投影；重启不能假装旧 oneshot 仍可回答 |
| [desktop notification](../../../../apps/desktop/src/electrobun/index.ts) | automation-alert 有系统通知出口；本轮未找到幕僚完成通知接入；Feishu 页有 notification.arm 调用，但不能据此认定通用服务存在 | 复用宿主展示能力，新增有持久来源的站内待办和投递适配 |
| [Task domain](../../../../crates/core/src/task.rs)、[Task Store](../../../../crates/core/src/task_store.rs) | 已有结果契约修订、work items、comments/suggestions 等类型和存储；本轮所查生产插件没有完整连接该运行路径 | 借用适用契约和测试，不为此启用完整 Scenes 2.0；当前幕僚目标只有一份权威状态 |
| [Memory contract](../../../reference/memory.md) | 已有来源、纠正、遗忘、回忆策略和预算 | 继续使用；工作消息、运行状态不写成长期事实 |

只给 JSON 增加 send/ask 两种动作仍缺消息归属、送达回执、问题寿命和变更版本。全面重写 Engine 会破坏可复用的权限和会话路径。选择：替换协调协议，补强共享消息投递，扩展既有幕僚工作区。

## 2. 管理对象与唯一数据源

- 项目简报：目标背景、约束、关键决定，引用既有项目和 Memory Store。
- 目标：用户想得到的结果、验收条件、优先级；语义变更增加 contract_revision。状态/优先级更新不冒充需求内容变更。
- 执行委派：归属目标、具体工作说明、负责会话、工作区、输入产物版本、依赖、contract_revision、控制权和授权来源。新尝试有独立 attempt_id；同一次请求重试保持 command_id。
- 会话：运行、等待输入、停止、失败等事实仍由 Engine/Activity 拥有；协调层只引用，不能改写。
- 协调记录：message、question、change、decision、review 和 delivery。结构化审计记录有唯一 id、关联目标/委派、作者身份、版本、来源及时间。站内收件箱和时间线是这些记录的投影。
- 记忆：经确认的稳定事实和决定；通过原有 Memory Store 管理。工作记录引用 memory_id，不复制另一份可写知识库。

目标、任务交付、通知分别有自己的事实：执行者提交结果 → 待验收 → 通过/返工/无法验证；通知同时可以未读。用户点击通知不会把目标标为完成。

首轮实现仍允许每个目标一个活动写入者，不新增通用 DAG 调度器。先支持跨目标的显式依赖/产物引用，拒绝循环；依赖产物变化使下游待复核。拆成多个独立目标可并行，同一目标的替换执行者要等旧执行者释放写入权。

## 3. 谁与谁沟通

| 方向 | 内容 | 生效条件 |
| --- | --- | --- |
| 用户 → 幕僚 | 交办、补充、改方向、调整优先级、停止 | 自然语言先解析成可见目标/变更；明确请求可直接记账，不逐步重复问批准；歧义才提问 |
| 幕僚 → 执行者 | 委派、补充、问题答复、纠偏、返工、停止请求 | 绑定当前委派和版本；关联观察不授予控制权 |
| 执行者 → 幕僚 | 阶段进展、问题、风险、变更建议、交付 | 经宿主绑定真实 session/assignment 身份；不能靠模型自填 id 冒充其他执行者 |
| 幕僚 → 用户 | 需要决定、重要变化、完成/失败通知、项目简报 | 有可打开的原问题、受影响任务及建议；同一问题合并，不刷屏 |
| 执行者 ↔ 执行者 | 输入材料、接口约定、交接 | 经目标关联的协调记录路由；只传必要资料，不能任意读取其他项目全文 |

每条指令区分：已持久记录、等待投递、提供方接受、执行者确认、执行结果。未知不是失败；提供方接受不是理解并采用。消息必须显示实际生效模式：立即补充、本轮结束后送达、等待停止后续接，或不支持。

## 4. 工具契约

UI 与模型走同一 Core 服务；模型侧可以用结构化决定，执行者侧通过已绑定会话身份的宿主工具暴露必要子集。不要把 CLI 文本解析当作可靠双向通信。

| 能力组（设计名称） | 作用和边界 |
| --- | --- |
| context.read | 读取授权项目的简报、目标、相关记忆、会话摘要和产物引用；按需展开，返回版本和来源 |
| goal.manage | 创建/修订目标、优先级、依赖；幕僚不能自行扩张用户目标或权限；语义修订生成 change |
| assignment.dispatch / link | 创建执行尝试或观察已有会话；幂等；明确拥有控制权还是只观察 |
| message.send / status | 双向持久消息，指定 recipient、assignment、contract_revision、reply_to、delivery_mode、command_id；可查询真实回执 |
| question.open / answer | 带背景、选项/自由输入、建议、影响、是否阻塞的问题；回答必须引用具体 question_id 和当前版本 |
| change.propose / apply | 记录旧要求、新要求、原因、成本及受影响委派；仅获授权的变更可 apply，不能用普通聊天绕过 |
| assignment.control | pause_followup / request_stop / resume / cancel / take_over；明确控制对象；停止请求不等于已停止 |
| progress.report | 当前进展、证据、下一步、风险或阻塞；避免凭 token 数或安静时间声称百分比完成 |
| result.submit | 提交产物版本、检查结果、未解决问题和所依据需求版本；只进入待验收 |
| review.record | 通过、返工或无法验证；绑定需求/委派/产物/检查版本；高风险按规则独立复核 |
| memory.propose / confirm / correct / forget | 确认的决定按全局或项目范围记忆；普通推测只留在问题/建议，不提升为事实 |
| inbox.list / acknowledge | 用户处理待办和已读状态；状态转移自动生成通知记录，模型不能自行发送“已完成”绕过验收 |

Provider 能力探测来自真实会话能力。模型输出无效、工具不可用或权限不足，返回结构化失败并保留待办；不能静默降级为已完成。

当前生产入口：UI 使用 `assistant.snapshot`、带 revision 比较的 `assistant.edit` 及既有 `memory.*` 命令。幕僚提交结构化决定，Core 核对范围、额度和事实；它不能直接写会话状态。执行者通过宿主注入的 `codetwo_coordination` MCP 使用六个工具：`context`、`progress`、`ask`、`propose_change`、`confirm`、`submit`。会话身份由宿主凭据绑定，工具参数不接受自填 session/assignment 身份。写操作的 command_id 和实际回执同事务持久化。

普通 `engine.queue`、`engine.steer` 和协调指令共用 `prompt_delivery`。原内存提示队列已移除。Provider 不支持即时补充时明确排队；重试不能把旧回合即时指令移到新回合。

## 5. 执行中交流与提问

- 简单补充且不冲突：原生 steering 可用则投递；否则持久排队到本轮结束，明确告知不能立即生效。
- 询问即时进展：读取现有进展与工具事件；没有新证据时标记未知，不为“问进度”擅自中断长命令。
- 结构化问题进入统一待办。已有明确决定/记忆且不改变授权的事实问题，可由幕僚引用来源回答；预算、产品取舍、目标变化、权限和不可逆动作由用户决定。
- 区分领域澄清与权限请求。answer_permission 保持现有具体审批路径；幕僚不能把常识回答当成授权。
- 等待必答问题时只暂停依赖该答案的工作；其他独立目标继续。没有答复不等于选择默认选项；期限到达只提醒/升级，不推断同意。
- 问题持久保留，但原 Provider 等待通道重启后可能失效。先核对；若失效，以关联旧问题的新一轮消息恢复，标明“旧请求已失效”，不回放过期 request_id。
- 人直接在执行会话回答时，同一问题关闭并同步到幕僚；人已接管后，幕僚只观察，不能重复代答。

## 6. 改方向是一项事务

例：原目标 v3 为密码登录，用户要求 v4 改用邮箱验证码。

1. 保存变更原因、差异、验收条件、授权来源，分配 v4；冻结依赖旧要求的后续派工/验收。保留 v3 和已有交付。
2. 找出受影响执行者和下游；已完成但不再适用的产物标记待复核，不删除。未受影响的工作继续。
3. 同范围小纠偏可用 steering；实质方向变化先请求停止，等 Engine 确认终态后再续接。停止失败/超时进入待处理，不创建第二个写入者。
4. 派发 v4 说明，要求执行者确认已采用的新要求和可保留/需放弃的工作；执行者不确认时不能宣称变更已落实。
5. 已保存的 v3 结果可以保留为历史，不能通过 v4 验收。迟到的答复、旧问题和旧审查结论均检查版本。
6. 同一事务提交新版本、废止旧待投递指令及生成投递意图；外部 Provider 调用在事务外。用 command_id、版本比较和持久回执恢复，不能声称跨进程 exactly-once。

“停止幕僚跟进”“停止某次执行”“取消目标”“接管会话”必须是四种不同操作。取消不撤销已经发生的外部效果，也不自动删除工作区/产物。

## 7. 通知与用户工作台

站内待办是权威来源，桌面通知是可关闭的提醒适配。关闭窗口不能删除未处理问题；Core 离线期间不承诺继续执行或通知。重连后从未读游标恢复。

通知类型：需要回答、需要授权、变更待落实/失败、执行失败、交付待验收、验收通过、验收失效。完成通知包含目标、交付链接、通过的检查和剩余限制；不把 TurnEnded 写成“任务完成”。

持久通知 key 由事实 id + 版本 + 类型确定；重试保持 key，重复事件不生成多条站内通知。系统通知无法保证已展示/用户已读时显示未知。发出、平台回执、已读、已处理分开。站内通知提供对应目标/交付和原执行会话的入口；长目标卡定位到标题。当前 Electrobun API 不提供通知点击回调，因此本版不承诺 OS 通知点击直达目标。外部飞书/邮件需要另外配置和授权，本方案不默认发送。

幕僚主界面围绕三个工作面：项目简报与目标、待你处理、交付与记忆。任务详情展示决定/通信时间线、实际投递状态、变更差异和原执行会话。交办输入是入口，结果落到目标卡和待办，不要求用户在大量聊天窗口中追踪。

## 8. 记忆如何随工作更新

用户确认“这个项目采用邮箱验证码”后，写入带来源/适用项目的决定记忆；旧决定被替代但保留历史。临时阻塞留在任务记录，不永久污染记忆。全局偏好必须由用户明确指定或确认，不能把一个项目的决定推广到全部项目。

新一轮恢复从目标版本、未处理问题、投递回执、已确认决定和产物开始。纠正/遗忘影响后续回忆；已经送到 Provider 的内容不能远程抹除。若遗忘涉及仍在运行的任务，应显示受影响委派并提供发送纠正的动作；不能只修改记忆库后声称执行者已经忘记。

## 9. 恢复、公平调度和失效边界

- 一次 SQLite 事务持久化决定及投递意图；网络/Provider 操作不持有事务。一个 Core 拥有该数据目录。
- 引擎队列持久化改造覆盖普通 UI 与幕僚调用；移除原内存私有队列。未知投递结果必须查询原命令，不盲重发；无法核对就呈现待处理。
- 全局 attention 只用于整个幕僚不能工作的故障。目标 A 等待回答/失败，不阻止独立目标 B；按优先级和等待时间防止低优先级饥饿。
- 事件聚合按语义变化唤醒；stream token、相同进展、模型自身摘要不触发反馈循环。通信、复查、返工都有有限额度，不把有限派工额度误认为所有成本有界。
- 任务身份由宿主绑定；用户权限和系统外部动作审批不因“来自幕僚”而绕过。问答/消息只能操作授权目标和当前委派。
- 删除/遗忘策略沿原数据所有者执行；消息不得夹带访问令牌。SQLite 迁移事务回滚，不能只升级部分字段。

首版边界：仍是有限额度的在线协调，不增加期限提醒调度器或历史归档。记录上限为 200 个目标、每目标 20 次尝试、1000 条消息、500 个问题/变更及 200 条交办；到达上限返回显式错误，不能静默删掉未处理工作。MCP 请求限 64 KB，并限制连接数和等待时间；凭据绑定不等于操作系统沙箱。未知网络结果保留待处理，不能承诺跨 Provider 的 exactly-once。

## Acceptance criteria

- [x] AC-1: 双项目中 A 提问等待，B 继续；用户与幕僚都能看到同一个问题及来源；答复只恢复受影响任务。
- [x] AC-2: 支持 steering 的 Provider 在运行中接受补充；不支持者持久排队且明确显示生效时间；不把回执当成采用。
- [x] AC-3: 运行中改需求 v3→v4；旧验收失效、旧指令废止、受影响执行者确认 v4 后继续；停止未确认前没有替代写入者。
- [x] AC-4: 幕僚只依据已确认事实代答；产品取舍与权限升级进入用户待办；过期答案和伪造任务身份被拒绝。
- [x] AC-5: 交付进入待验收，返工后才验收；验收通知含版本和证据；TurnEnded、哈希匹配、已读分别不能单独完成目标。
- [x] AC-6: 重复通知、断线、发送前后崩溃及未知回执不丢待办、不重复派工；恢复过期问题不向旧通道伪发送。
- [x] AC-7: 确认变更生成有来源的项目记忆；纠正/遗忘影响新回忆，并显示运行中受影响任务；普通推测不进入确认事实。
- [x] AC-8: 暂停跟进、停止执行、取消目标、接管均有不同状态和真实回执；观察关联不能改写会话；A 故障不冻结 B。
- [x] AC-9: 真实桌面/Web 界面验证交办、提问、答复、变更、投递状态和交付深链；桌面通知拒绝时站内待办仍可用。
- [x] AC-10: 首版数据迁移保留 id/会话/记忆/证据；旧 in-flight 派工不被重复发送；现有普通 Engine queue/steer/question 行为通过回归；生产仅一套投递路径。
