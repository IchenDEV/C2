# Spec: Builtin Chief Of Staff

## Design

本设计已由用户确认。下列首版边界、数据归属和恢复约束共同构成审阅对象；实现状态见 Verification。

## 已确认的首版决定

内置一个用户级幕僚，管理用户选定的多个项目。入口扩展现有 Mission Control，展示全局目标、进行中工作、待验收交付和需要用户决定的事项；用户也能自然语言交办、纠正目标和调整优先级。每个执行项都能打开原会话和产物，并可暂停、取消或接管。

幕僚负责判断和派工，不直接修改业务代码。它通过受范围约束的 CodeTwo 工具驱动现有 Engine 会话。普通执行会话继续使用现有工作台、模型设置和权限处理。首版不增加固定角色流水线或另一套任务执行器。

首版持续运行以拥有数据目录的 CodeTwo Core 进程在线为前提。关闭渲染窗口不会成为任务状态来源；Core 退出或机器休眠期间不承诺继续工作。恢复后核对持久记录再续接。跨设备常驻、云端控制面及外部 Bot 接入不在首版。

启用时用户选项目范围、模型配置、并发上限和自动推进额度；默认未启用。范围内已有授权覆盖的可逆工作继续推进。发消息、发布、合并、部署、删除、付费、账户连接与权限提升遵守已有具体操作授权。停止幕僚会禁止新派工，并明确显示仍在运行的执行会话；不会把执行者默认杀掉。

## 参考及取舍

- [poteto 的 pstack Orchestrate](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)：取任务说明、结果队列、版本绑定验收和恢复原则。未复制其多层代理、云端执行默认值或固定工具依赖。
- [Timothy 的帖子](https://x.com/timothyachumba/status/2106489967254098009)：通过公开文本接口读取，强调全局背景与可见、可接管的工作台结合；这是作者的使用体验，不是平台能力验收。
- [T3 /cos Gist](https://gist.github.com/uzairansaruzi/feab52b6d76b681d51d56dbcb5df23e6)：取简报、先检查已有工作、独立工作区和集中看结果。不照搬每一步等待 `go`、GitHub 作为所有记忆、每个执行者先停在计划的做法。
- istack 关联线程：幕僚与执行者分工、授权内自主推进。规则可借鉴，但本产品不能依赖另一工作区的绝对路径。

## 当前实现及方案选择

检查基线：`14c20fce`，初始工作区干净。近期 `7c099fd1` 已收敛会话编排并移除 Plan/Goal 控件，不恢复这些旧入口。

| 已有实现 | 首版处理 |
| --- | --- |
| `apps/desktop/src/sidebar/MissionControl.tsx` 及 `missionControl.ts` | 复用跨会话状态汇总；增加目标、派工及验收视图，不能把 idle 当成完成 |
| `crates/core/src/engine.rs`、Store、项目/会话命令 | 唯一执行路径；复用会话创建、提示、停止、工作区和真实活动状态 |
| `crates/core/src/automation.rs`、`apps/desktop/src-host/src/automation.rs` | 已有持久定时任务、事务领取与事件监听模式；当前每次运行新建会话，不等于可恢复的幕僚 |
| `crates/core/src/orchestrator.rs` | 只有内存 Planner/Executor 适配器和测试调用；不宣称已接入生产，不把首版绑到完整 Scenes 2.0 迁移 |
| `crates/core/src/engine.rs` 的 T3 创建/提示回执 | 有特定 T3 请求编码，普通 request_id 不代表持久去重；必须验证真实创建与提示边界 |

这是新增协调模块，不是局部缺陷。仅加 Skill 无法提供持久唤醒和全局状态；重写 Engine 或实现全部 Scenes 2.0 成本过大。选择现有运行模块机制下的可关闭内置功能，Core 拥有协调状态和工具，Core 模块持有低频时钟及事件订阅。

## 优先级补充

用户批准后补充“最重要的是记忆和项目管理”。首版优先提供可检查、可修正的项目记忆，以及目标、优先级、下一步、阻塞和验收的持久记录；派工使用同一份记录。复用现有 Memory Store 与删除/纠错策略，不另造记忆库。

## 唯一数据源与行为契约

- 项目、执行会话、运行状态、权限请求、产物仍由现有 Store/Engine 拥有。全局视图从这些事实派生，不另存一份可独立修改的执行状态。
- 新协调记录只拥有目标/验收条件、项目范围、授权引用、派工意图、关联的会话与产物版本、待处理事件、幕僚决定和验收结论。项目说明与目标记录提供重启上下文；聊天文本不是唯一记忆。
- 已存在且归属明确的执行工作可关联；仅凭标题相似不能接管或重复派工。关联不自动授予取消、改写、跨项目传递全文或外部发布权限。
- 每个派工包含目标、允许范围、输入引用、完成条件和配置。目标内首版至多一个活动执行者；独立目标之间受用户设置的总并发上限约束。模型变化必须来自用户。
- 幕僚默认取得范围内摘要；按需读取有来源的项目材料。跨项目传递最少必要上下文，不把所有聊天和文件拼进全局提示。
- “一轮结束”“进程退出”“本地检查通过”“验收通过”和“发布成功”是不同事实。验收引用具体提交/产物版本与证据；版本改变后旧结论失效。

## 唤醒、事务与关键不变量

1. 用户交办、被管理执行者的终态/阻塞变化及低频兜底检查产生唤醒。流式 token 不触发模型调用；无新事实时兜底检查不调用模型。自身简报更新不唤醒自身。
2. 唤醒依据先由现有 Store 持久化，协调记录保存已观察指纹与待处理回合；不另建事实队列。同一数据目录至多一个活动幕僚回合。写入决定采用修订校验，推理与外部执行不占 SQLite 事务。期间发生的变化由下一轮对账。
3. 派工意图必须先提交，再调用 Engine；关联创建回执后才算已派工。恢复时先查同一意图的持久回执与真实会话，不能靠超时重新创建。提示发送也需回执；结果不明时显示待核对，不盲目重放。
4. 同一目标不会同时重复派给两个写入者。用户暂停、接管或改变目标会增加修订号，使旧幕僚决定无法提交。取消未收到终态回执时不立即派替代执行者。
5. 事件流丢失、Core 重启或模型不可用时，从持久状态对账；有限重试，达到回合/派工额度或连续无进展上限后暂停并说明原因。没有真实用量时显示未知，不宣称货币预算已受控。
6. 协调工具在宿主核对项目范围和调用身份。提示词“不要改代码”不构成安全沙箱；实际能力和 Provider 的文件访问边界必须在集成验证中确认。

## 首版验收场景

用户交办“跟进 A 项目的登录修复，同时整理 B 项目的发布说明”。幕僚识别 A 已有执行者并关联，为 B 创建范围明确的执行工作。A 交付后核对版本和证据；需要修复则续派，缺少发布授权则集中展示决定。期间重启 Core，恢复后没有重复会话或重复提示，用户可打开任一执行会话接管。

## Acceptance criteria

- [x] AC-1: 在两个隔离示例项目中，幕僚汇总真实状态、识别已有工作，并派出有范围和验收条件的执行任务；不重复派工。
- [x] AC-2: 真实 Provider 完成一次派工、结果回传、版本绑定验收和失败后跟进；idle/EndTurn 不能自动满足业务验收。
- [x] AC-3: 重复/丢失事件、派工提交后崩溃及提示回执不明均经集成测试；恢复不产生重复执行，未知结果可见。
- [x] AC-4: 范围限制、模型选择、暂停/接管、额度和无进展停止经验证；过期决定不能覆盖用户操作。
- [x] AC-5: 全局入口实际渲染验证浅色、深色、窄窗口与键盘操作；用户能看到待决定事项、产物及执行会话并接管。
- [x] AC-6: 关闭/重新启用内置功能不会清除用户记录或终止无关会话；Core 离线与恢复边界清楚，现有普通会话及定时任务检查通过。
